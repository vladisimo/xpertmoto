# Prisma migration workflow

You are about to change the Prisma schema in this repo. The flow below is the
contract for getting from schema edit → working migration → green CI without
losing data or breaking the seed.

## Pre-flight

1. **Confirm intent in the user turn.** The `protect-schema.sh` PreToolUse hook
   blocks edits to `prisma/schema.prisma` unless the current user turn mentions
   `migration` or `schema change`. If the user hasn't said one of those, ask
   them to confirm before editing — don't try to bypass.
2. **Read the existing model** before editing. Many models in this repo are
   touched by jobs, services, and routers. Use `Grep` for the model name across
   `src/server/services/`, `src/server/jobs/`, `src/server/trpc/router/`,
   and `prisma/seed.ts` to understand the blast radius.

## Edit

3. Edit `prisma/schema.prisma`. Follow the existing patterns:
   - All models have `id`, `createdAt`, `updatedAt`. Most have `deletedAt`
     for soft delete.
   - Money fields are `Decimal @db.Decimal(12, 2)` — never `Float`.
   - Foreign keys are explicit `@relation(...)` with `onDelete: Restrict`
     unless the parent owns the child's lifecycle (then `Cascade`).
   - Add `@@index([...])` for any FK or commonly filtered field.
   - Enums live in `prisma/schema.prisma` itself, not in a separate file.

## Migrate

4. Run `npm run db:migrate -- --name <descriptive_snake_case>`.
   - Naming convention: read the last 5 entries in `prisma/migrations/` to
     match style. Examples: `add_vehicle_owner`, `infringement_dispute_fields`,
     `gift_card_balance_audit`.
   - **Never** use `prisma db push` — it skips the migrations directory and
     desyncs prod. The `guard-bash.sh` hook will block any `prisma db push`
     against a non-localhost DATABASE_URL.

## Breaking-change check

5. Diff the new migration's `migration.sql`. Flag to the user **before
   continuing** if it includes any of:
   - `DROP COLUMN` on a column that's `@unique`, referenced by a `@relation`,
     or appears in `prisma/seed.ts` / `tests/`.
   - `ALTER COLUMN ... NOT NULL` on a previously nullable column without a
     `DEFAULT` (will fail on existing rows).
   - `DROP TABLE` on any model whose name appears in `src/`.

   For breaking changes, propose a 2-step migration: (a) add the new column /
   table, (b) backfill in code or via a `data/` script, (c) follow up with a
   second migration that drops the old column.

## Regenerate

6. Run `npm run db:generate` (Prisma Client codegen). The PostToolUse
   `typecheck-changed.sh` hook will catch any consumer that still references
   the old shape.

## Seed + fixtures

7. Update `prisma/seed.ts` if the change adds a required field with no default
   or removes a field used in the seed. The minimal-snapshot fixture lives at
   `prisma/snapshots/minimal.sql` (reset target for `npm run db:reset`) — if
   the snapshot is out of date, regenerate it via `npm run db:reset:demo` then
   `pg_dump` per the existing pattern.
8. Update or add a Vitest test for any service whose query shape changed.
   Mirror rule: `src/server/services/X.ts` → `tests/unit/services/X.test.ts`.

## Confirm

9. Run `npm run typecheck && npm run lint` and report the result.
10. Summarise the change to the user in 2 lines: what changed, what's the
    blast radius (services / jobs / routers / seed touched).

## Skip / waive

- `CLAUDE_SKIP_HOOKS=protect-schema` only if the user has explicitly waived
  the keyword check for this turn — never silently.
- Generated Prisma Client (`node_modules/.prisma/`) is regenerated by
  `npm run db:generate`, never edited by hand.
